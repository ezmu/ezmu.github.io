The POSIX Manifesto

Why Bare-Metal and System Calls Will Always Win
Ez Eldeen Mushtaha · Engineering Manifesto First Principles · 2025

Introduction

There is a quiet war in software engineering that no one talks about.

On one side: the modern stack — containers, microservices, Kubernetes, Node.js, Python, garbage-collected runtimes, layers upon layers of abstraction.

On the other side: POSIX, C, and the bare metal — direct system calls, shared memory, epoll, zero-copy, static binaries, and the kernel as a trusted ally rather than a mysterious black box.

The modern stack has won the marketing war. It has won the conference talks. It has won the job titles.

But it has not won the performance war. And it never will.

This article is a manifesto. A return to first principles. A reminder that the kernel is not something to be afraid of — it is something to be understood and mastered.

Chapter One · The Golden Age of Rigor

What Is POSIX?

POSIX (Portable Operating System Interface) is a family of standards maintained by IEEE. It defines:

  • System call interfaces (open(), read(), write(), mmap(), epoll())
  • Process management (fork(), exec(), pthread_create())
  • Memory management (malloc(), free(), shm_open(), mlock())
  • File system operations (stat(), chmod(), fsync())
  • Networking interfaces (socket(), bind(), listen(), accept())

Why POSIX matters:

  • Portability: Code written to POSIX runs on Linux, BSD, macOS, and many other Unix-like systems.
  • Stability: POSIX interfaces have been stable for decades. Code written in 1990 still compiles and runs today.
  • Performance: Direct system calls have zero overhead. No garbage collector. No interpretation. No JIT compilation. Just the CPU and the kernel.

What Happened to the Golden Age?

In the 1990s and early 2000s, engineers wrote code that talked directly to the kernel.

  • Web servers were written in C (Apache, Nginx).
  • Databases were written in C (PostgreSQL, MySQL).
  • Operating systems were written in C (Linux, FreeBSD).

Then came the cloud era.

Suddenly, the goal was not performance. The goal was speed of development. The goal was deployment convenience. The goal was hiring ease.

And so the layers began:

JavaScript → Node.js → npm → Docker → Kubernetes → Service Mesh → ...

Each layer added convenience. Each layer also added overhead. But that was okay — hardware was cheap, and cloud providers were happy to sell more of it.

Chapter Two · The POSIX Toolbox

This chapter documents the tools available to an engineer who wants to build high-performance systems using POSIX directly.

1. Direct System Calls

What they are:

System calls are the interface between user-space applications and the kernel.

Examples:

System CallPurpose
open()Open a file
read()Read from a file descriptor
write()Write to a file descriptor
mmap()Map files or memory into the address space
epoll_create()Create an epoll instance
epoll_wait()Wait for I/O events
sendfile()Transfer data between file descriptors (zero-copy)
splice()Move data between file descriptors (zero-copy)
socket()Create a socket
accept()Accept a connection
recv() / send()Receive and send data

Why they matter:

  • Zero overhead: No garbage collector. No interpretation. No JIT.
  • Direct control: You control exactly what happens and when.
  • Predictable performance: No hidden pauses. No unexpected GC spikes.

2. Memory Management

A. mmap() — Memory-Mapped Files

What it does:

mmap() maps a file (or a portion of it) into the process's address space. The file becomes accessible as memory.

void *addr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, offset);

Why it matters:

  • Zero-copy: Data moves from disk to memory directly, without copying through user-space buffers.
  • Shared memory: Multiple processes can map the same file with MAP_SHARED and communicate through it.
  • Lazy loading: The kernel loads pages on demand (page faults), not all at once.

The cost:

OperationTime
Read from file with read()~100–500 μs (with copy)
Access mapped memory with mmap()~10–50 μs (page fault + direct access)

B. shm_open() — POSIX Shared Memory

What it does:

shm_open() creates a shared memory object that can be mapped by multiple processes.

int fd = shm_open("/my_shared_memory", O_CREAT | O_RDWR, 0666); ftruncate(fd, size); void *addr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

Why it matters:

  • IPC without sockets: Processes communicate through memory, not through network calls.
  • Zero serialization: No JSON, no gRPC, no protobuf. Just raw memory.
  • Microsecond latency: Access shared memory in ~100 ns instead of ~500 μs over TCP.

Comparison:

IPC MethodLatencyOverhead
TCP socket (local)~100–500 μsHigh
gRPC (local)~200–800 μsVery high
POSIX Shared Memory~100–200 nsZero

C. mlock() / mlockall() — Locking Memory

What it does:

mlock() prevents the kernel from swapping a range of memory to disk.

mlock(addr, size); // Lock a specific range mlockall(MCL_CURRENT | MCL_FUTURE); // Lock all memory

Why it matters:

  • No page faults: Once locked, memory is always in RAM.
  • Predictable latency: No swap-induced delays.
  • Real-time performance: Essential for low-latency systems.

D. Fixed Memory Pools

What they are:

Instead of allocating memory dynamically (malloc() / free()) during request processing, pre-allocate a fixed pool and manage it yourself.

// Pre-allocate pool #define POOL_SIZE 65536 struct pool_block { void *data; size_t size; }; struct pool_block pool[POOL_SIZE]; size_t pool_head = 0; // Allocate from pool void *pool_alloc(size_t size) { if (pool_head + size > POOL_SIZE) return NULL; void *ptr = &pool[pool_head]; pool_head += size; return ptr; }

Why it matters:

  • O(1) allocation: No heap traversal, no free list scanning.
  • No fragmentation: Fixed-size blocks prevent memory fragmentation.
  • No malloc overhead: malloc() can be surprisingly expensive (~100–500 ns per call).

Comparison:

Memory Allocation MethodTime
malloc() / free()~100–500 ns
Fixed memory pool~5–10 ns

3. I/O Event Notification

A. epoll — The Linux Event Notification Interface

What it does:

epoll is the Linux API for monitoring multiple file descriptors for I/O events.

int epfd = epoll_create1(0); struct epoll_event ev; ev.events = EPOLLIN; ev.data.fd = socket_fd; epoll_ctl(epfd, EPOLL_CTL_ADD, socket_fd, &ev); struct epoll_event events[MAX_EVENTS]; int n = epoll_wait(epfd, events, MAX_EVENTS, -1); for (int i = 0; i < n; i++) { handle_event(events[i].data.fd); }

Why it matters:

  • O(1) scalability: Scales with active connections, not total connections.
  • No polling: The kernel notifies the application when events occur.
  • Efficient: Supports millions of connections on a single server.

Comparison:

I/O ModelScalabilityLatency
select()O(N)High
poll()O(N)High
epoll()O(1)Low
io_uringO(1)Lowest

4. Zero-Copy Operations

A. sendfile() — Zero-Copy File Transfer

What it does:

sendfile() transfers data from a file descriptor to a socket descriptor without copying to user space.

off_t offset = 0; ssize_t sent = sendfile(socket_fd, file_fd, &offset, file_size);

Why it matters:

Traditional (4 copies): Disk → Kernel → User → Kernel → NIC Zero-copy (0 copies): Disk → Kernel → NIC

Comparison:

Transfer MethodCopiesContext SwitchesCPU Usage
read() + write()44High
sendfile()02Low

5. Threading and Scheduling

A. pthread — POSIX Threads

pthread_t thread; pthread_create(&thread, NULL, thread_function, arg); pthread_join(thread, NULL);

Why they matter:

  • Standardized: Works on Linux, BSD, macOS.
  • Lightweight: Threads share memory space.
  • Efficient: Context switching is faster than process switching.

B. sched_setaffinity() — CPU Pinning

What it does:

pthread_setaffinity_np() pins a thread to specific CPU cores.

cpu_set_t cpuset; CPU_ZERO(&cpuset); CPU_SET(0, &cpuset); // Pin to core 0 CPU_SET(2, &cpuset); // Pin to core 2 pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);

Why it matters:

  • Cache locality: The thread's L1/L2 caches remain warm.
  • No thread migration: The kernel doesn't move the thread to another core.
  • Predictable performance: Reduced context switching and cache misses.
Without pinning: Thread runs on core 0 → L1/L2 cache filled with data Kernel migrates thread to core 3 → L1/L2 cache is cold Cache misses → 10× slower With pinning: Thread stays on core 0 → L1/L2 cache remains hot → 10× faster

6. Advanced Optimization

A. TCP_NODELAY — Disable Nagle's Algorithm

int opt = 1; setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));

Comparison:

AlgorithmLatencyEfficiency
Nagle's (default)~20–200msHigh
TCP_NODELAY~1–5msLower

B. SO_REUSEPORT — Socket Load Balancing

int opt = 1; setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));

Why it matters:

  • Scalable: Each worker gets a separate socket and connection queue.
  • No lock contention: Workers don't compete for a single listen socket.
  • Kernel-level load balancing: The kernel distributes connections evenly.

C. io_uring — The New King of I/O

struct io_uring ring; io_uring_queue_init(256, &ring, 0); struct io_uring_sqe *sqe = io_uring_get_sqe(&ring); io_uring_prep_read(sqe, fd, buf, size, offset); io_uring_sqe_set_data(sqe, buf); io_uring_submit(&ring); struct io_uring_cqe *cqe; io_uring_wait_cqe(&ring, &cqe); // Process completion io_uring_cqe_seen(&ring, cqe);

Why it matters:

  • Zero system calls: The kernel reads requests from a queue, no syscall per operation.
  • Batch processing: Submit multiple operations at once.
  • High throughput: Supports millions of I/O operations per second.

Comparison:

I/O ModelSyscalls per operationThroughput
read() / write()2Low
epoll() + read()1–2Medium
io_uring0 (submission queue)Very high

D. DPDK — Kernel Bypass

What it does:

DPDK (Data Plane Development Kit) allows applications to bypass the kernel's network stack and talk directly to the network card.

Why it matters:

  • Ultra-low latency: Eliminates kernel overhead.
  • High throughput: Processes millions of packets per second.
  • Zero-copy: Packets go directly from NIC to application memory.

Comparison:

Networking ModelLatencyThroughput
Kernel TCP/IP stack~50–100 μsLow
io_uring~10–30 μsMedium
DPDK~1–5 μsVery high

Chapter Four · The Conclusion

Why POSIX Still Matters

1. Performance

POSIX systems run at the speed of the hardware. No garbage collector. No interpreter. No JIT compilation. Just the CPU and the kernel.

2. Predictability

No GC pauses. No throttling. No silent packet drops. Performance is deterministic.

3. Simplicity

A static binary is a static binary. Copy it. Run it. That is all.

4. Portability

POSIX code runs on Linux, BSD, macOS, and even some embedded systems.

5. Understanding

To write POSIX code, you must understand the kernel. You must understand memory. You must understand the network stack. This understanding makes you a better engineer.

The Fear of POSIX

Why don't more developers use POSIX directly?

Fear.

  • Fear of memory management (malloc() / free())
  • Fear of threads and locks
  • Fear of system calls
  • Fear of the kernel

But fear is not a valid engineering justification.

The kernel is not a mysterious black box. It is a well-documented interface that has been stable for decades.

The fear is learned. It comes from an industry that has taught developers to run away from the kernel, to hide behind layers, to trust that "someone else" will handle the performance.

It is time to unlearn that fear.

Final Words

The modern stack has its place. It is good for prototyping. It is good for teams that need to move fast. It is good for applications where performance is not critical.

But if performance matters, if latency matters, if efficiency matters — POSIX is the only answer.

The industry has spent 20 years adding layers. It is time to start removing them.

The kernel is your friend. The system calls are your tools. The memory is your playground.

Learn them. Master them. Use them.

Because the alternative is another layer, another container, another microservice, another cloud bill.

And that alternative is not engineering. It is hiding.

Appendix B · Fixed Memory Pool Implementation

#include <stddef.h> #include <stdint.h> #define POOL_SIZE 65536 struct pool_block { uint8_t data[POOL_SIZE]; size_t head; }; struct pool_block pool; void *pool_alloc(size_t size) { // Align to 8 bytes size = (size + 7) & ~7; if (pool.head + size > POOL_SIZE) { return NULL; // Out of memory } void *ptr = &pool.data[pool.head]; pool.head += size; return ptr; } void pool_reset(void) { pool.head = 0; } // Usage: void *buffer1 = pool_alloc(1024); void *buffer2 = pool_alloc(8192); // Process... pool_reset(); // Reuse the entire pool

Appendix C · epoll Event Loop Template

#include <sys/epoll.h> #include <unistd.h> #define MAX_EVENTS 1024 int epoll_event_loop(int listen_fd) { int epfd = epoll_create1(0); if (epfd < 0) return -1; struct epoll_event ev; ev.events = EPOLLIN; ev.data.fd = listen_fd; epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev); struct epoll_event events[MAX_EVENTS]; while (1) { int n = epoll_wait(epfd, events, MAX_EVENTS, -1); for (int i = 0; i < n; i++) { int fd = events[i].data.fd; if (fd == listen_fd) { // Accept new connection int conn_fd = accept(listen_fd, NULL, NULL); ev.events = EPOLLIN | EPOLLET; ev.data.fd = conn_fd; epoll_ctl(epfd, EPOLL_CTL_ADD, conn_fd, &ev); } else { // Handle data from existing connection handle_connection(fd); } } } close(epfd); return 0; }
