The Containers Fallacy

How a Joke Became an Industry Standard
Ez Eldeen Mushtaha · Engineering Manifesto First Principles · 2025

Introduction

Fifteen years ago, there was a joke among engineers:

"The code doesn't work on the server!"
"Strange! It works fine on my machine!"
"Then take your machine and give it to the customer!"

Everyone laughed. The implication was clear: a developer who cannot manage their environment, does not understand dynamic linking, and does not know how the kernel works, is someone who needs to return to fundamentals.

Then came the cloud era.

The industry had a choice:

  • Teach developers how to write code that respects POSIX, understands system calls, and manages memory directly.
  • Package the problem and sell it as a solution.

They chose option two.

Containers are not a solution. They are a workaround. They do not fix the problem—they encapsulate it, and ship it to production.

This article dissects the layers of abstraction we have built, the cost of each layer, why the industry's obsession with "adding layers" is not engineering, and why the "isolation" that containers claim to provide is an illusion.

Chapter One · The Five Layers of the Disaster

Layer One · The Networking Disaster

What Happens in Pure POSIX?

In a normal POSIX system, the application opens a socket and talks directly to the kernel network stack.

Application → Kernel Network Stack → Physical NIC

One hop. Zero translation. Zero overhead.

The application calls socket(), bind(), listen(), accept(), and recv()/send(). These are system calls. They go straight to the kernel. The kernel manages the TCP/IP stack, routing, and the NIC driver directly.

What Happens in Docker?

To run your application with -p 8080:80, every packet travels through:

Application → veth pair → docker0 bridge → iptables DNAT → conntrack → Kernel Network Stack → Physical NIC

That is six hops. Each hop has a cost.

Sub-Layer 1A: veth pair and Context Switching

Each container runs in its own network namespace. To connect this namespace to the host, the kernel creates a virtual Ethernet pair (veth). One end lives inside the container; the other lives in the host's root namespace.

Every packet that crosses between the container and the host must be transferred between two network namespaces. This transfer requires a context switch.

MetricValue
Cost of a single context switch~1,000–2,000 CPU cycles
Packets per second under moderate load50,000–100,000
CPU cycles wasted on context switches alone50–200 million cycles per second
Percentage of CPU spent on switching vs processing15–25%

Under higher load (200,000+ packets/second), this can reach 40% of CPU time wasted purely on moving packets between namespaces.

Sub-Layer 1B: iptables and DNAT/SNAT

Docker uses iptables to forward ports. When you map -p 8080:80, the kernel sets up DNAT rules:

iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
OperationCPU Cost
IP header modification~50–100 cycles
Port checksum recalculation~50 cycles
Routing table lookup~100–200 cycles
conntrack entry creation/lookup~200–500 cycles
Total per packet~400–900 CPU cycles

For 100,000 packets/second, that is 40–90 million CPU cycles per second spent purely on NAT and routing—before any application logic.

Sub-Layer 1C: The conntrack Table

The kernel maintains a connection tracking table (nf_conntrack) for NAT. Every active connection is tracked.

Default limit: 65,536 entries.

When the table is full, the kernel drops packets silently.

# You will see this in dmesg: nf_conntrack: table full, dropping packet.
Connections/secondEntries created per minuteTime to fill default table
1,00060,000~1 minute
5,000300,000~13 seconds
10,000600,000~6 seconds

Once the table is full, new connections are dropped without any application-level error. The developer sees unexplained timeouts, connection resets, and failures—but the application logs show nothing.

This is a silent failure. No exception. No stack trace. Just packets vanishing.

Sub-Layer 1D: Ephemeral Port Exhaustion

When Docker uses NAT for outgoing connections, it consumes host ephemeral ports.

sysctl net.ipv4.ip_local_port_range # Output: 32768 60999

That is 28,232 ports.

Connections per secondPorts consumedTime to exhaust
1,00028,23228 seconds
5,00028,2325.6 seconds
10,00028,2322.8 seconds

Once exhausted, new connections fail with:

EADDRNOTAVAIL (Cannot assign requested address)

Important distinction:

  • ulimit -n inside the container does not affect this.
  • This is a host-level kernel limit.
  • Even if your container is configured for 1,000,000 file descriptors, the host will still run out of ephemeral ports.

Layer Two · The Filesystem Disaster

What Happens in Pure POSIX?

The application calls open(), read(), write(), close(). The Virtual File System (VFS) looks up the file in the kernel's directory cache (dcache). The kernel reads the file from the disk or from the page cache.

Application → VFS → dcache → Page Cache → Physical Disk

What Happens in Docker OverlayFS?

Docker uses OverlayFS (or Overlay2). This is a union filesystem that combines multiple layers into a single view.

Container View │ ▼ ┌─────────────┐ │ Upperdir │ ← Writable layer (container-specific) │ (writable) │ └─────────────┘ │ ▼ ┌─────────────┐ │ Lowerdir 1 │ ← Read-only (image layer 1) └─────────────┘ │ ▼ ┌─────────────┐ │ Lowerdir 2 │ ← Read-only (image layer 2) └─────────────┘ │ ▼ ┌─────────────┐ │ Lowerdir N │ ← Read-only (image layer N) └─────────────┘

Sub-Layer 2A: Layer Lookup Overhead

When the application calls open("/some/file"):

  • Search upperdir for the file.
  • If not found, search lowerdir 1.
  • If not found, search lowerdir 2.
  • Continue through all lower directories.
  • Return the first match.

Sub-Layer 2B: Copy-on-Write (CoW) Disaster

When the application modifies a file that exists in a lower layer:

  • OverlayFS pauses the process.
  • The entire file is copied from the lower layer to the upper layer.
  • The modification is applied to the copy.
  • The process resumes.

Layer Three · The CPU Scheduler Disaster

What Happens in Pure POSIX?

The Linux Completely Fair Scheduler (CFS) schedules processes based on their nice values and CPU usage. No artificial limits. No throttling.

Process → CFS → CPU Core

What Happens with cgroups and CFS Bandwidth Control?

Docker uses cgroups to limit CPU usage. This uses the CFS Bandwidth Control feature.

cpu.cfs_period_us = 100000 (100ms) cpu.cfs_quota_us = 150000 (150ms) # When --cpus=1.5 is set

Chapter Two · The Isolation Illusion

Docker claims to provide "isolation" between containers. This claim is technically false.

1. Security Isolation is Not Real

All containers on the same host share the same kernel.

CVE-2019-5736runc2019Critical

CVE-2022-0492cgroup v12022High
CVE-2023-25173containerd2023Critical
CVE-2024-21626runc2024Critical
"Containers do not provide the same level of security as virtual machines. The kernel is shared between containers and the host." — Docker Documentation

2. Network Isolation is Not Real

  • All containers share the same network stack on the host.
  • veth pairs and bridges connect containers to the host network.
  • NAT and iptables mean containers are not isolated from the host or from each other.

3. Filesystem Isolation is Not Real

  • All containers share the same kernel VFS and same page cache.
  • Modifications in the upperdir are container-specific, but lower layers are shared.

4. CPU and Memory Isolation are Not Real

  • All containers share the same CPU cores and same memory bus.
  • cgroups set limits, but do not provide real isolation.
  • CFS throttling freezes containers, but does not prevent cache contention.

5. Kernel Resource Isolation is Not Real

  • conntrack table is shared across all containers.
  • dentry and inode caches are shared.
  • arp and route tables are shared.

Chapter Four · When Containers Make Sense

When Containers Make Sense

  • Development environments: Consistency between dev, test, and production.
  • CI/CD pipelines: Reproducible build and test environments.
  • Multi-team organizations: Teams manage their own dependencies.
  • Legacy applications: Package applications that are difficult to refactor.
  • Rapid prototyping: Quick experimentation without affecting the host system.

When Containers Do NOT Make Sense

  • High-performance systems: The overhead is too high.
  • Low-latency applications: Networking and scheduling overhead cause spikes.
  • Simple applications: Complexity is disproportionate to benefit.
  • Single-binary deployments: A static POSIX binary is simpler, smaller, and faster.
  • Security-critical systems: Shared kernel and container escape risks are too high.

Chapter Five · Root Cause Analysis

  • The Industry Chose Convenience Over Discipline — Easier to add a library than to write code. Easier to add a layer than to understand one.
  • Developers Stopped Learning the Fundamentals — Many cannot explain how malloc() works, or what a system call is.
  • Cloud Providers Profited from Inefficiency — AWS, GCP, and Azure make money when you consume more resources.
  • The Philosophy Became "Ship Everything" — Instead of shipping just the application, we ship the entire environment.

Chapter Six · The Alternative

Pure POSIX Architecture

  • Static Binary: All dependencies linked at compile time. Zero runtime dependencies.
  • Direct Kernel Communication: System calls directly. No layers of daemons.
  • Predictable Performance: No GC pauses. No throttling. No silent packet drops.
  • Minimal Resource Consumption: 2–10MB RAM, 200KB–5MB disk.
  • Simplified Deployment: Copy the binary. Run it. That is all.
  • Real Isolation (If Needed): Separate physical machines or VMs with their own kernels.

Chapter Seven · The Conclusion

The joke we used to laugh at—"It works on my machine"—became an industry standard.

We stopped teaching developers how to write portable, standards-compliant code.

We stopped teaching them what malloc() does, how the kernel schedules processes, or why the network stack is designed the way it is.

We replaced engineering rigor with layers.

We replaced understanding with abstraction.

We replaced real isolation with administrative illusion.

And now we wonder why our systems are slow, unstable, insecure, and expensive to operate.

The industry does not need another layer. It needs a return to fundamentals.

It needs to stop shipping the environment and start shipping the solution.

It needs to stop wrapping the garbage and start fixing it.

It needs to stop pretending that containers provide isolation and start understanding what isolation actually means.

Because the joke stopped being funny a long time ago.
